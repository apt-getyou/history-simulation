# 史料溯源与偏倚控制方案

## 目标

确保历史模拟器的每条断言都有可追溯的证据链，并标注来源的视角偏倚，防止叙事依赖造成的假交叉验证。

## 一、数据源分层

### 第一层：原始文献（断言的直接依据）

必须下载到本地，存入 `data/sources/primary/`。

- 正史、实录、起居注
- 奏疏、诏令、书信、日记、笔记
- 地方志（原始版本）、碑刻、出土文书
- 当事人文集

### 第二层：学术著作（断言的补充依据）

必须下载到本地，存入 `data/sources/secondary/`。

- 考古发掘报告
- 学术专著（大学出版社、权威出版社）
- 核心期刊论文
- 研究者整理的史料汇编（标注编者信息）

### 第三层：线索参考（不进入断言链）

不可作为任何断言的直接依据。仅用于发现检索线索。

- 维基百科、百度百科等可编辑百科 -- 发现"该查什么原始文献"
- 博客、论坛帖子 -- 发现线索
- AI 生成摘要 -- 严格禁止

**规则：第三层来源发现线索后，必须追溯到第一/二层原始文献验证，才能形成断言。**

## 二、本地文献库结构

```
{sim-slug}/
└── data/
    └── sources/
        ├── catalog.json              # 文献总目录（元数据 + 偏倚标注）
        ├── primary/                  # 第一层：原始文献
        │   ├── 三国志.txt
        │   ├── 后汉书.txt
        │   └── ...
        ├── secondary/                # 第二层：学术著作
        │   ├── 吕思勉-三国史话.txt
        │   └── ...
        └── evidence/                 # 证据链文件（随模拟器一起交付）
            ├── 诸葛亮-evidence.json
            ├── 曹操-evidence.json
            ├── 赤壁之战-evidence.json
            └── ...
```

### 文献入库规则

1. 文件入库时计算 SHA-256 哈希，写入 catalog.json
2. 入库文件内容只读，不可修改
3. 如需校勘或注释，另存为新版本文件（文件名加后缀 `_v2`），原始文件保持不变
4. 文件编码自动检测（UTF-8 / GBK / Big5），无法解码时报错

## 三、文献目录 catalog.json

每份入库文献必须登记。AI 辅助填写偏倚标注，用户确认后锁定。

### 字段定义

```json
{
  "files": [
    {
      "id": "sgz",
      "filename": "三国志.txt",
      "tier": "A",
      "source_type": "primary",
      "author": "陈寿",
      "author_identity": "蜀汉旧臣，入晋后任著作郎",
      "completion_period": "西晋（约280-290年）",
      "edition_note": "中华书局点校本",
      "bias_annotation": {
        "political_stance": "西晋正统视角，以魏为正朔",
        "known_gaps": "对蜀汉早期记载简略，对东吴内政记载较少",
        "known_embellishments": "无明显文学虚构",
        "reliability_assessment": "high",
        "assessment_detail": "正史中最接近三国时期的记载，但受政治立场影响对曹魏有所回护"
      },
      "narrative_dependencies": [],
      "file_hash": "sha256:abcdef...",
      "file_size": 450000,
      "reading_strategy": "chapter"
    }
  ]
}
```

### 偏倚标注字段说明

| 字段 | 含义 | 填写方式 |
|------|------|---------|
| `political_stance` | 作者的政治立场/正统观 | AI 从作者身份和文本内容推断，用户确认 |
| `known_gaps` | 已知的内容空白区 | AI 辅助 + 用户补充 |
| `known_embellishments` | 已知的夸大或虚构部分 | AI 辅助 + 用户补充 |
| `reliability_assessment` | 整体可靠性评估（high/medium/low） | AI 建议，用户确认 |
| `assessment_detail` | 可靠性评估的理由 | AI 生成初稿，用户可修改 |

### 叙事依赖关系 narrative_dependencies

记录本文献在编写时参考过哪些其他文献。用于识别假交叉验证。

初始为空数组。在冲突检测阶段（Phase 2）由 AI 识别可疑情况，用户确认后写入。

## 四、证据链设计

每个实体（人物、势力、事件、制度等）对应一个证据链文件，记录所有断言及其溯源。

### 文件位置

`data/sources/evidence/{entity}-evidence.json`

### 文件结构

```json
{
  "entity_name": "诸葛亮",
  "entity_type": "person",
  "last_updated": "2025-01-15T14:30:00",
  "assertions": [
    {
      "id": "A001",
      "claim": "诸葛亮字孔明，琅琊阳都人",
      "category": "basic_identity",
      "assertion_strength": "strong",
      "evidence": [
        {
          "source_id": "sgz",
          "source_tier": "A",
          "location": "蜀书·诸葛亮传，第一段",
          "exact_quote": "诸葛亮字孔明，琅琊阳都人也",
          "bias_note": "基础身份信息，无明显偏倚风险"
        }
      ],
      "corroboration_type": "single_primary_source",
      "corroboration_detail": "单一一手来源，但此类基础信息无争议",
      "confidence": "high",
      "dispute": null
    }
  ]
}
```

### 断言强度规则

沿用 `source-policy.md` 的断言入库规则，并扩展：

| 强度 | 条件 | 模拟器中的处理 |
|------|------|-------------|
| `strong` | 一手史料直接支持，或两条独立来源交叉支持 | 可写入硬规则 |
| `weak` | 仅有单一二手来源，或来源间存在冲突 | 标注为"倾向""可能" |
| `disputed` | 来源间存在不可调和的矛盾 | 标注所有版本，供用户在冲突解决中选择 |
| `fiction` | 文学创作/演义虚构，非史实 | 标注来源类型，按用户选择的蓝本策略决定是否纳入 |
| `inferred` | 无直接史料，从行为/环境推断 | 标注推断逻辑，不可作为硬规则 |

### 交叉验证类型

| 类型 | 含义 | 置信度影响 |
|------|------|-----------|
| `independent_primary` | 两个或以上独立一手来源交叉支持 | high |
| `single_primary_source` | 单一一手来源支持 | high（基础信息）/ medium（评价类） |
| `primary_plus_secondary` | 一手来源 + 学术研究支持 | high |
| `narrative_dependent` | 多个来源但存在叙事依赖（非真正独立） | 降一级 |
| `single_secondary` | 单一学术来源 | medium |
| `absence_vs_addition` | 正史无载 vs 文学有载 | low（作为史实）/ 视蓝本策略决定 |

### 偏倚叠加检测

在冲突检测阶段（Phase 2）增加偏倚叠加检查逻辑：

**触发条件**：多个来源对同一事实的记载高度一致（措辞相似度 > 80%）。

**AI 执行步骤**：
1. 检查这些来源是否共享同一叙事传统
2. 检查 catalog.json 中的 narrative_dependencies 字段
3. 如果发现潜在依赖关系，标记该断言的 `corroboration_type` 为 `narrative_dependent`
4. 向用户展示："以下来源记载高度一致，可能存在传抄关系，请确认：[来源A] [来源B] ..."
5. 用户确认后，更新 catalog.json 的 narrative_dependencies 字段

**用户确认选项**：
- [A] 确认存在传抄依赖 -- 降级交叉验证
- [B] 确认独立来源 -- 保持原验证等级
- [C] 不确定 -- 标记为待定，按 narrative_dependent 处理

## 六、与现有阶段的对接

### Phase 0（访谈）-- 改造

新增"本地文献清单"收集环节：

1. 询问用户已有哪些原始文献资料
2. 询问用户已有哪些学术著作
3. 询问用户是否有特定版本的偏好（如中华书局点校本 vs 其他版本）
4. 生成文献收集任务清单

### Phase 1（数据收集）-- 改造

1. 先处理本地文献（现有逻辑不变）
2. AI 辅助填写 catalog.json 的偏倚标注，用户确认
3. Web 搜索降级为补充角色：
   - 搜索目标改为"寻找第一/二层来源的在线版本"而非直接采信搜索结果
   - 搜索结果中发现的线索，必须追溯到原始文献验证
   - 在搜索结果中标注 `discovery_source: "web_search"`，区别于本地文献

### Phase 2（冲突检测）-- 改造

1. 冲突检测前，先检查涉及的来源是否存在叙事依赖
2. 冲突严重度评估增加偏倚因素：
   - 如果冲突双方中一方存在明显政治偏倚，在 agent_notes 中标注
   - 如果冲突源于不同叙事传统（如正史 vs 民间记载），标注为"叙事传统差异"
3. 新增偏倚叠加检测步骤（见第四节）
4. 冲突解决后，将断言写入对应的 evidence.json 文件

### Phase 3（人物提炼）-- 改造

1. 提炼每条人物信息时，关联 evidence.json 中的断言ID
2. 提炼结果中不可出现无断言ID支撑的关键信息
3. 如果某条信息无证据支持，必须标注为 `inferred` 并写明推断逻辑

### Phase 6（生成）-- 改造

1. 生成的目标模拟器 skill 包中包含 `evidence/` 目录
2. `evidence/` 目录作为交付物的一部分，包含所有实体的证据链文件
3. 目标模拟器的 source-ledger.md 使用增强模板

### Phase 7（验证）-- 改造

新增验证项：

1. 检查所有断言是否有至少一条证据支撑
2. 检查所有 strong 断言是否满足交叉验证条件
3. 检查是否存在未确认的偏倚标注
4. 检查是否存在疑似叙事依赖但未标记的情况

## 九、偏倚标注工作流

### 步骤

1. 文献入库时，AI 根据文献元数据（作者、时代、身份）生成偏倚标注初稿
2. AI 阅读文献序言/凡例/跋等部分，补充偏倚信息
3. 将初稿展示给用户，逐项确认或修改
4. 用户确认后锁定偏倚标注
5. 后续如有新发现（如学术研究指出该文献某部分不可靠），可追加标注

### AI 辅助偏倚推断的依据

- 作者身份与政治立场（如蜀汉旧臣写西晋官修史书）
- 编写时代与所记事件的时间距离（越近越可靠，但政治压力也越大）
- 作者在文本中自述的编写原则
- 已知学术研究对该文献的评价
