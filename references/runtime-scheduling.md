# 运行时人物调度设计

## 核心问题

模拟器运行时，上下文窗口是有限资源。如果把所有人物卡全塞进上下文：

- 50 个人物 × ~500 token = 25,000+ token
- 大部分与本回合无关
- 关键人物的信息被淹没在噪声中
- 回合质量随人物数量增加而下降

**结论：不能每回合全量加载人物卡。必须按需加载。**

---

## 设计原则

1. **按需加载**：只加载本回合相关的人物信息
2. **分层精度**：不同相关性的人物，加载不同粒度的信息
3. **上下文预算**：每回合有 token 预算，人物信息不能超过总预算的一定比例
4. **调度与数据分离**：调度逻辑决定加载谁，加载的内容是纯数据

---

## 三层人物数据结构

人物信息不是一块铁板，而是天然分层的三级结构：

### 第一层：总览表（常驻上下文）

**始终加载，体积极小。** 所有活跃人物各占一行。

格式：表格形式，每行一个人物。

```
| 姓名 | 状态 | 身份 | 阵营 | 位置 | 与主角关系 | 本回合标记 |
|------|------|------|------|------|-----------|-----------|
| 刘备 | 活跃 | 左将军 | 荆州 | 新野 | 君主 | 无 |
| 诸葛亮 | 活跃 | 军师 | 荆州 | 新野 | 主角本人 | 本回合焦点 |
| 曹操 | 活跃 | 司空 | 许都 | 许昌 | 对手 | 西线军情涉及 |
| 孙权 | 活跃 | 讨虏将军 | 江东 | 吴 | 潜在盟友 | 无 |
| ... | ... | ... | ... | ... | ... | ... |
```

**token 成本**：50个人物 ≈ 1000-1500 token（可控）

**用途**：
- 调度器快速扫描谁在什么位置、属于什么势力
- 确定本回合需要加载哪些人物的详细信息
- 信息不对称判定：快速检查某人是否"应该知道"某事

### 第二层：摘要卡（按需加载）

**仅加载与本回合相关的人物。** 每个摘要卡约 100-150 token。

格式：压缩段落，不是完整人物卡。

```
## 诸葛亮 [摘要]
军师将军，蜀汉阵营，当前在新野。
公开目标：辅佐刘备，兴复汉室。
当前压力：曹操南征在即，荆州危殆。
近期行动倾向：主张联合孙权抗曹。
与主角关系：本人。
认知边界：不知曹操内部密谋，不知孙权真实态度。
```

**加载判定规则**：

以下条件满足任意一条，即加载该人物的摘要卡：

| 条件 | 说明 |
|------|------|
| **主角本人** | 始终加载完整信息 |
| **同场景** | 与主角在同一地点或同一事件中 |
| **本回合事件涉及** | 被任何已触发事件直接点名 |
| **信息传播链** | 本回合有信息传递到该人物 |
| **主角主动互动** | 玩家指定要与该人物互动 |
| **主动接触主角** | 该人物本回合主动来找主角 |
| **关键势力代表** | 其所在势力正经历重大变化 |

### 第三层：完整人物卡（深度加载）

**极少数人物，仅在需要精细化决策时加载。** 每张约 400-600 token。

完整人物卡包含七层模型的全部信息。

**加载条件（更严格，同时满足摘要卡条件 + 以下至少一条）**：

| 条件 | 说明 |
|------|------|
| **需要做复杂决策** | 该人物面临多方博弈、利益冲突的决策 |
| **主角深度互动** | 密谈、谈判、审讯、劝说 |
| **性格偏离检查** | GM 需要判断该人物的行为是否偏离性格模型 |
| **新经历塑造性格** | 该人物经历了重大事件，需要更新性格档案 |
| **玩家特别关注** | 玩家要求了解该人物的详细信息 |

## 回合调度流程

```
回合开始
  │
  ▼
[Step 1] 加载总览表（常驻，约1000 token）
  │
  ▼
[Step 2] 结算天气、气候、时间推进
  │
  ▼
[Step 3] 扫描事件引擎，确定本回合触发的事件
  │        → 事件可能点名涉及特定人物
  │
  ▼
[Step 4] 确定本回合需要加载的人物清单
  │
  │        输入：
  │          - 总览表中的人物位置和状态
  │          - 本回合触发事件涉及的人物
  │          - 主角当前场景中的其他人物
  │          - 信息传播链上的人物
  │
  │        输出：
  │          - 摘要卡加载列表（通常 5-15 人）
  │          - 完整卡加载列表（通常 1-3 人）
  │
  ▼
[Step 5] 按需加载人物摘要卡和完整卡
  │
  ▼
[Step 6] 执行回合结算（天气 → 事件 → 人物行动 → 主角行动 → 状态更新）
  │
  ▼
[Step 7] 信息传播结算
  │        → 逐人物判定：他应该知道什么？
  │        → 只基于摘要卡的认知边界字段
  │        → 不需要加载完整卡
  │
  ▼
[Step 8] 输出结果、更新记录、更新 state.json
  │
  ▼
[Step 9] 人物卡变更写回
  │        → 如果本回合某人物经历了重大事件，更新其性格档案
  │        → 变更写回对应文件，不影响其他人物
  │
  ▼
回合结束
```

## 上下文预算控制

每回合的上下文有硬性 token 预算：

```yaml
context_budget:
  total: 8000            # 总预算（token）

  allocation:
    world_rules: 1500     # 天气、事件引擎、状态规则等常驻内容
    overview_table: 1500  # 总览表
    summaries: 3000       # 摘要卡（约 20 人）
    full_cards: 1500      # 完整卡（约 3 人）
    output_buffer: 500    # 预留给输出
```

**当预算紧张时**：

1. 优先保留摘要卡，减少完整卡
2. 优先保留与主角同场景的人物
3. 远方势力代表降级为总览表中的一行
4. 如果摘要卡也超预算，按与主角的距离排序，先砍最远的

## 信息不对称的轻量判定

信息不对称判定不需要加载完整人物卡。只需要摘要卡中的一个字段：

```
认知边界：不知曹操内部密谋，不知孙权真实态度。
```

调度器在信息传播结算时，逐条检查：

```
对于每条本回合新增的信息：
  1. 该信息的传播范围是什么？（公共/势力内/私密）
  2. 逐人物检查摘要卡的"认知边界"字段
  3. 该人物是否在传播范围内？
     - 是 → 标记为"本回合可知"
     - 否 → 不标记
  4. 如果该人物是主角，只告知标记为"本回合可知"的信息
```

这个流程只需要总览表 + 摘要卡，不需要完整卡。

## 完整人物卡的存储位置

完整人物卡不在上下文中常驻，而是作为独立文件存储：

```
{sim-slug}/
├── characters/           # 人物卡存储目录
│   ├── active/           # 活跃池
│   │   ├── liubei.md     # 完整人物卡
│   │   ├── zhugeliang.md
│   │   └── ...
│   ├── waiting/          # 等待池（待出生人物的条件卡）
│   │   ├── zhugejun.md
│   │   └── ...
│   └── archive/          # 归档池（已故人物）
│       ├── old_minister.md
│       └── ...
├── data/
│   ├── overview.md       # 总览表（自动生成，每回合更新）
│   └── summaries/        # 摘要卡（自动生成，每回合更新）
│       ├── liubei.summary.md
│       ├── zhugeliang.summary.md
│       └── ...
```

**自动同步规则**：

1. 总览表从 `characters/active/` 的所有人物卡头部提取，每回合自动重新生成
2. 摘要卡从完整人物卡压缩生成，只生成调度器判定需要的人物
3. 完整人物卡仅在需要时由调度器读取，不自动加载

## 摘要卡生成规则

从完整人物卡压缩为摘要卡的规则：

| 完整卡字段 | 摘要卡处理 | 示例 |
|-----------|-----------|------|
| 姓名、身份、阵营 | 直接保留 | "军师将军，蜀汉阵营" |
| 当前位置 | 直接保留 | "当前在新野" |
| 公开目标 | 压缩为一句话 | "辅佐刘备，兴复汉室" |
| 隐藏压力 | 压缩为一句话 | "曹操南征在即，荆州危殆" |
| 近期行动倾向 | 压缩为一句话 | "主张联合孙权抗曹" |
| 与主角关系 | 保留标签 | "本人" |
| 认知边界 | 保留（关键字段） | "不知曹操内部密谋，不知孙权真实态度" |
| 天性基底 | 不保留 | -- |
| 已成型特质 | 不保留 | -- |
| 未成型特质 | 不保留 | -- |
| 诚实边界 | 不保留 | -- |
| 详细关系网 | 不保留 | -- |
| 说话风格 | 不保留 | -- |

**压缩比**：完整卡 ~500 token → 摘要卡 ~100 token（5:1）

## 与现有架构的关系

本设计不改变生成阶段（阶段 0-8）的产物，只改变运行时的加载方式：

| 生成产物 | 存储为 | 运行时使用方式 |
|---------|-------|--------------|
| 完整人物卡（03-cast-registry.md） | `characters/active/*.md` | 按需读取，不常驻上下文 |
| 总览表 | `data/overview.md` | 每回合自动从活跃池生成，常驻上下文 |
| 摘要卡 | `data/summaries/*.md` | 每回合按需从完整卡压缩生成 |

目标模拟器 `SKILL.md` 中的回合流程需要增加 Step 4（确定加载清单）和 Step 5（按需加载）。
