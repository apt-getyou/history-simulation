# 阶段 3.2：世界审核与补充设定

## 定位

阶段 0 的访谈是粗粒度的——用户在看到完整世界之前，很难给出精确的补充设定。

本阶段在人物提炼（阶段 3）完成后执行，此时世界已具雏形、人物卡已生成。向用户展示已构建的世界和人物，收集细粒度的补充设定。

## 触发条件

阶段 3 完成后**必须执行**。

## 输入

- `data/distilled/character-inventory.md`（人物清单）
- `data/distilled/*.yaml`（人物提炼档案）
- `data/generation-brief.md`（现有 custom_injections）

## 输出

| 文件路径 | 内容说明 |
|---------|---------|
| `data/distilled/user-supplements.yaml` | **用户补充设定汇总**。包含：世界观补充、人物额外设定、新增人物清单。每条设定标注来源（用户原始描述），留待阶段 5 做规则化 |
| `data/distilled/{new_character}.yaml` | **新增人物提炼档案**。按阶段 3 的七层模型生成，标注为 `source: user_added` |
| `data/distilled/character-inventory.md`（更新） | **人物清单更新**。新增人物加入清单，修改人物标记 `modified: true` |
| `data/generation-brief.md`（更新） | **生成简报更新**。将 `custom_injections` 扩展，加入本阶段收集的补充设定，标注 `phase: 3.2` |

**持久化要求：** 每轮交互确认后立即将结果写入磁盘。新增/修改的人物档案在生成后立即写入。不要等待阶段全部完成。

## 执行流程

```
3.2.0 展示世界总览
  │
  3.2.1 人物总览确认
  │
  3.2.2 核心人物逐个审核
  │
  3.2.3 世界观补充问答
  │
  3.2.4 人物额外设定
  │
  3.2.5 新增人物
  │
  3.2.6 写入全部结果
```

### 3.2.0 展示世界总览

向用户展示已构建世界的概要：

```
世界：{sim_name}
时代：{historical_anchor}
起点：{start_date}
主角：{protagonist}
真实性模式：{fidelity_mode}

已有设定：{列出 custom_injections 中的现有设定}

人物统计：核心 {N} 人 / 重要配角 {N} 人 / 次要人物 {N} 人 / 背景人物 {N} 人
势力数量：{N}
```

询问用户是否需要调整世界基本设定。如需调整，记录变更并更新 `generation-brief.md`。

### 3.2.1 人物总览确认

向用户展示人物总览表（从 `character-inventory.md` 提取）：

| 姓名 | 类型 | 派系 | 与主角关系 | 数据丰富度 | 可塑性 |
|------|------|------|-----------|-----------|--------|

询问：

> 以上是当前世界中的所有人物。
>
> 1. 名单是否完整？是否有遗漏的重要历史人物？
> 2. 是否需要移除某个人物？
> 3. 是否需要调整某个人物的类型（如从"次要"提升为"重要配角"）？

根据用户反馈更新清单。移除的人物标记为 `excluded: true` 而非删除。

### 3.2.2 核心人物逐个审核

**仅对核心人物和重要配角执行此步骤。** 次要人物和背景人物只展示清单，不逐个展开。

对每个核心/重要配角：

1. 展示该人物的提炼摘要（非完整七层档案，而是压缩版）：

```
人物：{name}
身份：{identity} | 派系：{faction} | 位置：{location}

公开目标：{public_goal}
隐秘压力：{hidden_pressure}
与主角关系：{protagonist_relation}

核心特质：{列出 3-5 个关键行为特征}
知识边界：{知识截至 start_date 的状态}
```

2. 询问用户：

> 这个人物的设定是否符合你的预期？
>
> - 是否需要补充背景故事、特殊经历或隐藏设定？
> - 是否需要调整其与主角的关系或态度？
> - 是否需要为其添加特殊能力或知识（如架空设定）？

3. 收集用户补充，记录到 `user-supplements.yaml` 的 `character_supplements` 部分。

格式：

```yaml
character_supplements:
  - character: 张居正
    supplements:
      - type: hidden_setting        # hidden_setting / special_ability / relationship / backstory
        description: "用户原始描述"
        phase: 3.2
```

每确认一个人物，立即将补充内容写入 `user-supplements.yaml`。

### 3.2.3 世界观补充问答

向用户提出开放式问题，引导补充世界细节：

> 世界和人物已经基本成型。现在可以补充更详细的设定：
>
> **1. 世界规则补充**
>    - 是否有未提及的制度、法律、习俗需要特别关注？
>    - 是否有特殊的地理特征或资源分布需要补充？
>    - 是否需要增加天气/气候的特殊影响规则？
>
> **2. 势力关系补充**
>    - 是否有未体现的势力间暗中关系？
>    - 是否有隐藏的联盟或敌对关系？
>
> **3. 剧情与事件补充**
>    - 是否希望某些特定事件在模拟中发生？
>    - 是否有想要探索的历史假设场景？
>
> **4. 氛围与风格补充**
>    - 对叙事风格是否有额外要求？
>    - 是否有希望融入的文化元素或典故？

收集的回答记录到 `user-supplements.yaml` 的 `world_supplements` 部分：

```yaml
world_supplements:
  - category: institution           # institution / faction / event / atmosphere
    description: "用户原始描述"
    phase: 3.2
```

### 3.2.4 人物额外设定

如果用户在 3.2.3 中提到了人物相关的补充，此步骤进行针对性收集。

对每个需要额外设定的人物，确认：

1. **设定类型**：特殊能力 / 隐藏身份 / 额外关系 / 特殊物品 / 剧情触发条件
2. **可见性**：谁可以看到这个设定（仅 GM / 特定人物 / 特定势力 / 公开）
3. **触发条件**：这个设定在什么条件下会激活或暴露
4. **影响范围**：影响哪些系统（政治/财政/军事/民情/天气）

收集的回答追加到 `user-supplements.yaml` 的 `character_supplements` 部分。

### 3.2.5 新增人物

询问用户是否需要添加新人物：

> 是否需要向这个世界添加新的人物？
>
> **A. 历史人物** -- 真实存在但未被自动收集的历史人物
> **B. 虚构人物** -- 完全由你设计的原创人物
> **C. 不需要添加**
>
> 如需添加，请描述：
> - 人物名称（历史人物需要可考证的姓名）
> - 身份和角色
> - 在这个世界中的定位
> - 与主角的关系
> - 任何特殊设定

#### 处理新增历史人物

对于历史人物（类型 A）：

1. 检查是否在 `data/raw/` 中已有数据
2. 如有数据，执行阶段 3 的提炼流程生成七层档案
3. 如无数据，通过搜索收集基础史实后提炼
4. 标注 `source: user_added`、`character_type: historical_added`
5. 在人物清单中标记 `added_in_phase: 3.2`

#### 处理新增虚构人物

对于虚构人物（类型 B）：

1. 根据用户描述生成七层档案
2. 以下层必须由用户明确提供或确认：
   - 动机层（公开目标 + 隐秘利益 + 红线）
   - 关系层（与已有人物的关系）
   - 诚实边界层（全部标注为 `[I001]` 推断，来源标记为 `user_design`）
3. 以下层可以合理推断：
   - 制度位置层（基于其身份推断）
   - 决策启发层（基于动机推断）
   - 压力反应层（基于身份和动机推断）
4. 标注 `source: user_added`、`character_type: fictional`
5. 出生条件（如果涉及阶段 3.4）：需明确其父母/家族背景

#### 批量处理

新增人物按 5-10 人一批处理，每批完成后立即写入档案文件。

### 3.2.6 写入全部结果

确认所有交互完成后，执行最终写入：

1. 将 `user-supplements.yaml` 完整写入（已逐步写入的内容做最终确认）
2. 更新 `character-inventory.md`（新增/排除/修改的人物）
3. 更新 `generation-brief.md` 的 `custom_injections` 字段，将本阶段收集的全部设定追加上去，每条标注 `phase: 3.2` 以区分来源
4. 更新 `.generation-progress.json`，阶段 3.2 标记为 `completed`，`current_phase` 推进到 `3.4`

## 新增/修改人物对后续阶段的影响

| 后续阶段 | 需要的适配 |
|---------|-----------|
| 阶段 3.4 生态层 | 新增人物纳入出生条件检查、血统注册、死亡系统。虚构人物需补充家族背景 |
| 阶段 4 事件建模 | 用户新增的事件线索纳入事件卡。新增人物参与的事件需补充触发条件 |
| 阶段 5 规则形式化 | 本阶段收集的全部补充设定（世界观 + 人物 + 事件）统一进入规则化。`user-supplements.yaml` 是阶段 5 的输入之一 |
| 阶段 6 包生成 | 新增人物生成完整人物卡。修改人物的档案反映补充设定 |
| 阶段 7 验证 | 新增/修改人物的一致性纳入验证范围 |

## 上下文管理

本阶段交互轮次取决于人物数量和用户补充的丰富度。

**预估消耗：**
- 世界总览 + 人物清单确认：1-2 轮
- 核心人物审核：每人物 1 轮（如有补充则 2 轮）
- 世界观补充：1-2 轮
- 新增人物：每人物 1-2 轮

**如上下文不足：**
- 已处理的补充设定已持久化到 `user-supplements.yaml`
- 中断后恢复时，跳过已审核的人物，从未审核的核心人物继续
- 进度文件记录当前正在审核的人物名称

## 与阶段 5 的协作

本阶段**不做规则化**。只收集用户的原始描述。

规则化统一在阶段 5 执行，流程：
1. 阶段 5 读取 `custom_injections`（来自阶段 0）
2. 阶段 5 读取 `user-supplements.yaml`（来自本阶段）
3. 合并后统一做机制具象化、边界约束、人物交互、交叉验证
4. 产出 `custom-rules.yaml`

这样保持单一规则化出口，避免同一设定在多处被不同方式处理。
